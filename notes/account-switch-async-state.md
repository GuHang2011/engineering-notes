# 账号切换时的异步状态隔离

这篇记录复盘一次工作台提醒回归。它总结了复现方法、修复思路和验证边界，不包含产品源码、真实账号或业务数据。

## 发现的问题

账号 A 打开工作台后，提醒摘要请求仍在等待时切换到账号 B。前端把所有账号的待处理请求放在同一个 Promise 里，B 的刷新因此复用了 A 的请求，没有发出自己的请求。A 的响应又因当前账号已变化而被丢弃，B 的提醒区就会继续显示未加载状态，直到下一次刷新触发请求。

这是本轮发现的用户可见问题。原回归用例通过延迟 A 的响应并立即切换到 B 稳定复现；修复前，B 的请求次数为 0。

同一场景还暴露了第二个边界：如果旧账号的请求后来返回 HTTP 401，通用 Axios 拦截器会把当前账号的令牌清掉并触发登录跳转。修复前，旧账号 C 的 401 会让已经切换到账号 D 的页面失去登录态。

## 修复方式

- 用用户 ID 和会话令牌识别当前请求所属的登录会话；不同会话各自发起请求。
- 为每轮请求分配序号。仅当会话和序号都仍匹配时，响应、错误和清理逻辑才可以更新共享提醒状态。
- 新会话建立时清空旧账号的提醒数据、错误和加载状态，避免账号间短暂显示串号数据。
- 请求发出时保存会话令牌；401、4031 等认证响应只有在令牌仍属于当前会话时才允许执行全局登出或改密跳转。
- 增加浏览器回归用例：延迟账号 A 的响应，切换到账号 B 并验证 B 能独立完成加载；最后再放行 A，确认迟到响应不能覆盖 B 的数据或清除 B 的加载状态。
- 回归用例再延迟账号 C 的 401，切换到账号 D，确认 D 的令牌、用户和当前 URL 不会被旧响应改变。

## 同轮检查修复

全量 TypeScript 检查还发现三处类型问题：路由守卫把 `undefined` 和路径字符串放进同一个 `next` 调用；样式表规则被当成通用 `CSSRule`；空数组在严格模式下被推断为 `never[]`。已将路由跳转改为明确分支，为 CSS 规则和结果数组补上类型，随后全量检查通过。

宝塔部署说明仍指向旧压缩包名称。本轮同步更新为 2026-10-26，并注明没有数据库结构变更。

- Edge 148 的账号切换回归通过：A、B、C、D 均各自发出请求；B 先正确加载；迟到的 A 响应没有覆盖 B 的状态；C 的旧 401 没有清除 D 的令牌或触发跳转。所有接口均由本地测试夹具模拟。
- 六组已有浏览器回归通过，覆盖办公、聊天、AI、布局、浏览器兼容和会话流程；教师任务浏览器检查的十项场景通过。

- 新宝塔包（2026-10-26）的 CRC、资源引用和清单检查通过；从包内提取的实际后端 JAR 在隔离 MySQL 和临时目录中启动并完成接口冒烟。检查未连接或修改生产服务。
