# 大文件传输：分片只是可靠性的起点

聊天系统需要传输大附件时，将一个大请求拆成多个小分片，可以降低单次请求失败的代价，也让浏览器能展示进度和重试。但要可靠完成，还需要定义边界、幂等性、鉴权和清理策略。

## 实践中的参数

项目采用 4 MiB 分片和 1 GiB 文件上限。一个完整 1 GiB 文件正好是 256 个分片。浏览器在当前页面内支持暂停、继续、失败重试和取消；页面刷新后需要重新选择文件，不能把它描述为跨设备或跨会话断点续传。

## 传输协议需要回答的问题

- 每次上传都校验登录状态、群成员权限、上传记录归属和分片序号。
- 重复提交同一分片或重复完成请求应幂等，不能重复拼接或创建两条文件消息。
- 服务端按流写磁盘，不要把整份 1 GiB 文件读入 JVM 堆内存。
- 未完成上传要有过期清理和配额；磁盘不足、网络中断、服务重启时返回可理解的错误。
- 完成后才对群成员显示文件。下载和范围请求也必须重新验证授权，不能仅凭可猜测的文件路径访问。
- 通过 SHA-256 等摘要验证端到端文件一致性；需要法律或业务审计时另行定义保留策略。

## 网关和浏览器边界

代理限制应覆盖“单个分片请求”的尺寸，而不是把代理放开为可接收整个大文件。下载使用浏览器原生流式保存和 HTTP Range 支持，避免前端把整个文件装入 `Blob` 再复制一份内存。部分浏览器会拦截自动保存，保留用户点击的下载入口作为回退。

本项目的一次 1 GiB 测试使用 256 个分片完成上传和下载，并校验 SHA-256 一致。它验证的是单文件链路，不是高并发带宽能力。项目还没有病毒扫描；生产环境应配置磁盘监控、备份、内容扫描和过期文件策略。进一步阅读：[HTTP Range Requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Range_requests)。
